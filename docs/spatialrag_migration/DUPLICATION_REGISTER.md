# Duplication Register — spatial-rag vs. thehub-pr overlap

Phase 0 audit deliverable. Companion to [ADR 0003](../adr/0003-evidence-intelligence-control-plane.md).

Where spatial-rag's approach and thehub-pr's existing approach overlap or would collide if merged
carelessly. This is the check that prevents duplicate infrastructure from being built twice under
different names.

| # | Concern | spatial-rag approach | thehub-pr existing approach | Verdict |
|---|---|---|---|---|
| 1 | Document/text retrieval | Hybrid BM25 + vector + spatial search over ingested PDFs/images | `src/hub/mcp_runtime/adapters/documents.py` — case-insensitive substring search/read over local `.md`/`.txt` files, serving the `documents` MCP capability | **Not a collision.** Different capability level (substring search vs. hybrid retrieval over embeddings). No overlap to resolve now. Flag as a Phase 5+ (post-cutover) candidate for the Intelligence Engine to eventually supersede or extend `documents.py`'s capability surface — not touched in Phase 0-4. |
| 2 | Evidence tiering | `_assign_evidence_tier()` keyword classifier, `evidence_tier` DB column on `entities`/`citations` | No equivalent concept anywhere in thehub-pr today | **Net-new.** No overlap; thehub-pr's canonical streams carry `lineage`/`confidence`/`_producers` provenance but nothing resembling a tier. Design proceeds per [`DATA_CONTRACTS.md`](DATA_CONTRACTS.md) §2 without reconciling against a prior thehub-pr model. |
| 3 | Snapshot / versioning | None — spatial-rag's retrieval queries live mutable Postgres directly, no history | None — `src/hub/ingest.py`/`bridge.py` do `INSERT OR REPLACE` into `data/hub.db`, fully idempotent overwrite-in-place, no history table, no point-in-time query | **Both repos share this gap.** This is not a spatial-rag-specific defect to fix by copying a better thehub-pr pattern — thehub-pr has the identical gap. [`SNAPSHOT_STATE_MACHINE.md`](SNAPSHOT_STATE_MACHINE.md) is genuinely new work for both sides of the merge, and closing it in the Evidence/Control-Plane split should prompt a follow-up question (tracked in [`READINESS_REPORT.md`](READINESS_REPORT.md)) about whether `hub.ingest`'s overwrite pattern should eventually be revisited too. |
| 4 | Credential handling | `config.py` — plain `pydantic_settings.BaseSettings` reading `ANTHROPIC_API_KEY`/`API_KEY` from `.env`, no redaction guarantee | `src/hub/mcp_runtime/auth.py` — `CredentialProvider` protocol, `TokenCache`, fail-closed secret resolution, explicit `redact()` helper | **thehub-pr's pattern is strictly better.** Adopt `CredentialProvider`/`redact()` for any Evidence/Intelligence Engine API keys (embedding provider, LLM provider, geocoder); do not port spatial-rag's `config.py` credential loading. |
| 5 | Policy / capability governance | None — spatial-rag has no capability-declaration concept; access control is a single opt-in API key | `src/hub/mcp_runtime/policy.py` — `PolicyEngine`, declared-capability allowlists, read-only-by-default write policy, deprecated-capability blocking | **No spatial-rag analog exists.** `PolicyEngine` is the base the Control Plane's permissions layer extends (per ADR 0003); nothing to reconcile from spatial-rag's side because it never had this layer. |
| 6 | CI / build pipeline | `.github/workflows/ci.yml` inside the zip — content not deeply audited in this pass (out of scope for a doc-only Phase 0; the archive's CI config was skimmed for presence, not correctness) | `.github/workflows/ci.yml` — `pytest -q` + `ruff`/`mypy` on `src/hub`, a uv lock-check job, separate `frontend` (lint/test/build) and `frontend-visual` (Playwright) jobs, plus isolated CI for `packages/prii_maintenance` and `packages/prii_export_utils` | **Follow thehub-pr's precedent.** thehub-pr's per-surface job split is the pattern new engine CI jobs should extend (e.g. an `evidence-engine` job, an `intelligence-engine` job) in Phase 2+. spatial-rag's own CI config is explicitly flagged **unverified** here — its correctness was not confirmed in this audit pass and should not be assumed reliable; confirm independently in Phase 1 if any of its logic is worth referencing. |
| 7 | Spatial/geodesy math | PostGIS `ST_Distance`/`<->` nearest-neighbor queries, `geopy`-based Nominatim geocoding (unused) | `src/hub/correlate.py::_haversine_km` (pure Python, no DB extension), reused by `mcp_runtime/adapters/geospatial.py` for haversine distance/nearest queries | **Different tiers, not a collision.** thehub-pr's haversine math operates on structured records (no spatial database engine); spatial-rag's PostGIS operations are index-backed geometry queries over ingested documents. Evidence Engine's spatial handling (§6 of [`DATA_CONTRACTS.md`](DATA_CONTRACTS.md)) needs PostGIS-class capability that thehub-pr does not have today — see [`DATABASE_BOUNDARIES.md`](DATABASE_BOUNDARIES.md) for the resulting new-datastore decision. `correlate.py`'s haversine logic remains the right tool for structured-record correlation and is not replaced. |
| 8 | Entity linking | spaCy NER + co-occurrence edges (`entity_edges` table), no contradiction preservation | `src/hub/correlate.py` — normalized-name, external-id, location, funding-date, alert, and observation-footprint matching via `derive_relationships()`, also no contradiction preservation | **Both are linking-only, neither preserves contradiction.** Neither side's mechanism is adopted wholesale; [`DATA_CONTRACTS.md`](DATA_CONTRACTS.md) §5's contradiction-preserving model is new-build informed by `correlate.py`'s shape (grid-indexed matching, dedup-by-basis) rather than a port of either. |
